# 愿望开发

Development 承载贯穿普通会话的开发状态：原始愿望、范围与方案共创、准确版本确认、单 Agent 实施、真实验证、交付说明及用户验收。源码中的领域划分用于明确状态所有权；产品交互始终在同一会话中。它复用现有 Application、Plan、Goal、Runtime、Permissions 与 Shell；Core 不依赖本领域。

## 使用

在新建或已有工作区会话里直接描述希望创建、修改或修复的内容。模型自然调用 `wish_begin` 保留当前人类请求并调查项目，不需要特定关键词、模式开关、额外表单或独立导航。纯解释、代码阅读、状态询问和明确要求只读分析的消息直接在会话中回答。

1. 探索 Run 读取项目、提出少量关键问题，并用 `wish_propose` 保存目标、范围、约束、验收标准及实施方案。讨论阶段的源码写入与进程执行由权限策略实际阻止。
2. 会话中的「开发目标」显示紧凑状态，按需展开目标、方案和进展。「查看方案并确认」会展开准确版本的完整内容，确认绑定规格、完整 Plan 产物及源码基线，沿用 Plan 的人工审阅接口。
3. 单 Agent 按已确认版本实施，调用 `wish_verify` 通过现有 Shell、授权与 Sandbox 链路运行检查。退出码、保留输出、执行来源和实际源码快照由 Host 记录，模型没有 `passed` 输入。
4. `wish_report` 保存变更说明、逐项验证结果、限制和后续修改入口。所有技术标准具备当前有效的成功证据后，用户才能接受交付；主观标准由此次人工接受确认。
5. 会话内暂停会先撤销新实施授权，再等待自有运行停止；普通「停止运行」也会令开发状态进入暂停。「恢复」核对当前工作区并创建新 Run。修改需求时直接在原会话说明变化，保留原始愿望并追加修订，重新探索和确认；接受交付后仍可继续直接提出下一项需求。

支持一个本地工作区、一个活动开发增量、单 Agent。正式批准、开始/恢复及用户验收通过会话内的精确版本人工控件完成；仅在聊天中说“开始”不代替这些动作。CLI 可使用同一模型侧探索工具，完整人工操作界面目前位于 WebUI 会话。

## 领域与执行边界

- Project 保存稳定 ID、工作区绑定、会话关联与开发增量。不支持目录移动、多个 worktree 的自动合并及多 Host 写入。
- Spec 修订不可变，区分要求、假设、决策与待确认问题；验收项具有稳定 ID。Host 捕获提案时的源码基线并纳入完整摘要，首次确认前源码变化要求重新调查。
- Plan 仍拥有人工审阅。Development 封存正文、产物引用、准确审阅回执和规格的完整确认身份，不改变既有正文 digest 的含义。
- 启动操作先保存请求身份与完整输入摘要，再预留 RunId、绑定现有 Runtime。相同请求返回原回执，不同输入冲突；崩溃留下的未决操作要求核对，不声称跨系统恰好执行一次。
- Goal 只推进本次执行，Todo 只表示回合进度。Run 结束、Goal 完成、检查成功与用户接受是不同事实。
- Application 的通用 SessionFeature Run 通知提供包含实际清理的运行句柄，普通聊天开启的探索也参与暂停、交接与插件卸载检查。未结束的探索不能被部分批准并启动另一个 Run。
- 实施中的新用户输入先收紧旧授权。模型判断为编码需求时，通过 Host 封存正文与已接受的输入记录匹配，记录修订；当前 Run 收尾后自动继续只读探索，新的方案仍需人工确认。解释或状态询问不会被当作需求修订。
- 权限投影和调用时检查绑定 project/change/spec、RunId、executionEpoch 与 confirmation。暂停、修订、报告提交立即收紧旧 Step；同工作区另一 Session 不能绕过活动增量。开发执行期间关闭子 Agent 与 Workflow 写操作。
- 评估记录复杂度、不确定性、风险及流程强度；高风险不能标为轻量。评估结果不自动选择或编排不同强度的流程。

## 源码与验证证据

`snapshot.ts` 对实际文件字节生成摘要，包含未提交和未跟踪文件；它不把通用 Workspace revision 当代码快照。不调用 Git reset、checkout 或其他恢复写入。默认上限为 20,000 个文件、128 MiB 总量、16 MiB 单文件，拒绝符号链接、特殊文件及扫描中的内容变化。

快照明确记录排除项：`.git`、`node_modules`、`.wish`、`.env`/`.env.*`、`.aws`、`.ssh`、`.codex`、`.agents`。因此该身份描述选定源码集合，不能证明外部服务、环境变量或被排除内容相同。`dist`、`build` 等产物不会被静默排除；验证若生成或改变这些文件，先完成生成，再对稳定状态重新检查。

验证记录保存命令、退出码、超时、时间、实际 Run/Tool 身份、最多 16 KiB UTF-8 输出尾部及摘要。执行前后源码不同，或者绑定已过期，不生成成功证据。命令退出零只支持关联检查，不自动证明任意需求正确；验收标准与检查方法仍需要审阅。

报告和必要验证内容由 Project 独立持久保存。删除来源 Session 会按原语义停止运行、删除聊天和工具归档，并解除项目关联；项目愿望、方案及已封存报告继续可读。不提供删除项目或原调用栈恢复；删除会话后可在同工作区新会话开启后续增量。

实施中遇到需要新决策的阻塞，可用 `wish_report` 保存未完成项及所需输入。该报告保持未验证状态，不能被接受；产品停止自动实施，用户在当前对话补充需求，或选择继续开发与验证。

## 装配与生命周期

默认配置注册 `development` Provider、Context/Policy、模型工具、Session 清理适配和 WebUI control；界面通过独立 `DevelopmentClientUi` 与 UiSlots 贡献。`WISH_DEVELOPMENT_ENABLED=0` 可关闭该产品能力；关闭 Plan 时同步关闭依赖它的产品装配。

Storage 使用独立 `development/projects` 与 `development/operations` Domain，继承 Backend 的 schema/CAS 与进程内单写 Host 保证。管理停用/代码替换遇活动产品 Run 会报告 blocked，先暂停后可安全装卸；进程退出清理只停止该 Owner 的运行。Provider 恢复将未结束启动标记 interrupted，不自动重放。

## 验证

```sh
npm run typecheck
npm run test:development
npm run test:development:browser
npm test
```

专项覆盖领域/CAS、真实 Plan 与 Goal 交接、请求重放与崩溃意图、权限交集、真实 Shell、源码失效、独立证据、UI 状态与 managed 装卸。HTTP 集成使用本机确定性模拟 Provider，实际经过 Runtime、Tools 和 Shell；浏览器专项使用真实 Chromium 和桌面/移动视口。它们分别提供装配、实际工具、浏览器证据，不代表真实外部模型质量、公开部署或量化性能收益。
